# Create a payout

Sends USDT, USDC or a network's own coin from your API account to an external
address. Knit checks the balance, holds the amount, and submits the transfer.

<Endpoint method="POST" path="/api/v1/payouts" />

<Meta>
  <Scope value="payouts:write" />
  <Chip label="Auth" value="Bearer token" />
</Meta>

## Before you call

1. **The API account must exist and be funded.**
   [Create it](/API-account/create-an-API-account) for the token you are paying
   out, then fund it from the dashboard or let collections credit it. A short
   balance is rejected with `400`, and nothing is held.
2. **Your server IP must be allow-listed.** Requests from other addresses are
   rejected before reaching this endpoint.
3. **The destination address must be valid for the network.** Addresses are
   checked per chain; a malformed or wrong-chain address fails with `400`.
4. **The network must hold enough of the token.** Network liquidity is the
   amount of a token your business holds on one network. It is separate from
   your API account balance. A payout needs its amount plus fee in both, or it
   fails with `400` `Insufficient network liquidity`. Check
   [Network liquidity](/API-account/get-network-liquidity) first.

## Supported networks

| Network | Identifier |
| ------- | ---------- |
| Ethereum | `ETHEREUM_MAINNET` |
| Polygon | `MATIC_MAINNET` |
| Tron | `TRON_MAINNET` |
| BNB Smart Chain | `BSC_MAINNET` |
| Solana | `SOL_MAINNET` |

<Callout type="warning">
  Payout availability is narrower than collection availability — a network that
  accepts collections may not support payouts. Check `payoutStatus` in
  [`GET /api/v1/networks`](/networks/get-supported-networks) before you build
  against a chain.
</Callout>

## Coins

Each network's own coin can be paid out on that network only.

| Coin | Network | Decimals | Smallest payout |
| ---- | ------- | -------- | --------------- |
| `ETH` | `ETHEREUM_MAINNET` | 18 | 0.0005 |
| `BNB` | `BSC_MAINNET` | 18 | 0.001 |
| `POL` | `MATIC_MAINNET` | 18 | 0.5 |
| `TRX` | `TRON_MAINNET` | 6 | 1 |
| `SOL` | `SOL_MAINNET` | 9 | 0.005 |

A coin payout needs an [API account](/API-account/create-an-API-account) for
that coin. Send the amount as a string to keep all of its decimals.

## Paying a Knit address

You can pay out USDT or USDC to an address that another Knit business owns,
for example a deposit address of that business's wallet. Knit credits that
business once, after the network confirms the payment. Very small amounts are
credited too.

These Knit addresses are refused with `400`, and nothing is held:

| Message | Cause |
| ------- | ----- |
| `This address is a one-time Knit payment address and cannot receive payouts.` | The address belongs to a collection, a payment link or a deposit link |
| `This Knit address does not receive deposits on this network. Ask the recipient for their address on this network.` | The address is a Knit wallet address, but not on the `network` you pay out on |
| `Coins cannot be paid out to a Knit address. Pay out USDT or USDC, or use an address outside Knit.` | The payout is a coin (`ETH`, `BNB`, `POL`, `TRX` or `SOL`) and the address belongs to Knit |

## Body

<Fields>
  <Field name="network" type="string" required>
    One of the payout networks above.
  </Field>
  <Field name="token" type="string" required>
    `USDT`, `USDC`, or the network's own coin from the table above. Any other
    coin and network pair is rejected with `400`.
  </Field>
  <Field name="amount" type="number | string" required>
    The amount to send, in token units — not fiat. Minimum `0.01` for USDT and
    USDC. For a coin, at least its smallest payout, with no more decimals than
    the coin has.
  </Field>
  <Field name="toAddress" type="string" required>
    The destination address. Validated against the format and checksum rules of
    the chosen network.
  </Field>
  <Field name="merchantReference" type="string" required>
    Your own reference for this payout. It must be unique across all Knit
    businesses, not only yours. This is what makes retries safe. Use
    references that only you generate, for example your company name plus an
    invoice ID.
  </Field>
</Fields>

<Callout type="warning">
  `merchantReference` is **required**, not optional. Generate it from something
  stable on your side — an invoice ID, a ledger entry ID — so that replaying a
  request whose outcome you are unsure of is rejected as a duplicate rather
  than sending the money twice.
</Callout>

## Reusing a reference

Knit checks `merchantReference` before the balance and network checks. A
request with a reference that is already in use always gets the duplicate
`400` shown under [Errors](#errors), and nothing is held or sent. This is also
true for a retry with the same body that arrives while the first request is
still being processed. Read `errors.merchantReference` to detect it.

Always retry with the same reference and the same body. If you are not sure of
the outcome, send it again and wait for a definite answer: `201` or the
duplicate `400`.

To find the payout that holds a reference, call
[List payouts](/payouts/get-all-payouts) with `?merchantReference=`.

## Request

```bash filename="cURL"
curl -X POST "https://api-prod.useknit.io/api/v1/payouts" \
  -H "Authorization: Bearer $KNIT_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "network": "MATIC_MAINNET",
    "token": "USDT",
    "amount": 25.5,
    "toAddress": "0x56adfcc254ab3b8142a275c1837bcffaff5aa38b",
    "merchantReference": "INV-2045"
  }'
```

## Response

Returns `201`. The payout starts at `PENDING` — it has not settled on-chain
yet.

```json filename="201 Created"
{
  "statusCode": 201,
  "message": "Payout created successfully",
  "data": {
    "id": "8e5697e3-8265-455b-984a-0eb40e10b0f9",
    "businessId": "b7b93a40-4e18-4e97-9c5f-8a7a4fd0df92",
    "network": "MATIC_MAINNET",
    "token": "USDT",
    "amount": "25.500000000000000000",
    "toAddress": "0x56adfcc254ab3b8142a275c1837bcffaff5aa38b",
    "merchantReference": "INV-2045",
    "transactionHash": null,
    "status": "PENDING",
    "info": null,
    "createdAt": "2024-08-27T13:44:20.000000Z",
    "updatedAt": "2024-08-27T13:44:20.000000Z"
  },
  "success": true
}
```

## Status lifecycle

| Status | Meaning |
| ------ | ------- |
| `PENDING` | Accepted and queued. The balance has been held |
| `PROCESSING` | Submitted for settlement; awaiting on-chain confirmation |
| `COMPLETED` | Confirmed on-chain. `transactionHash` is populated and a `PAYOUT_SUCCESSFUL` webhook is delivered |
| `FAILED` | Could not be submitted for settlement. Check `info` for the reason. Knit retries it automatically, and `nextRetryAt` shows the next attempt. When Knit stops retrying it and knows nothing was sent on chain, you receive a [`PAYOUT_FAILED` webhook](/webhooks/payout-failed) |
| `CANCELLED` | Cancelled by Knit support. Knit does not retry it automatically, but support can still send it until it is refunded. When support refunds it, the held amount returns to your API account and you receive a `PAYOUT_REFUNDED` webhook |

<Callout type="warning">
  Do not send a `FAILED` or `CANCELLED` payout again under a new
  `merchantReference`. Knit retries a `FAILED` payout automatically with the
  same payout, up to 4 times within 48 hours, and its amount stays held. A
  second payout for the same recipient can then be paid as well.

  If a payout stays `FAILED` or is `CANCELLED`, contact Knit support. Send a
  new payout with a new `merchantReference` only after support has refunded the
  old one. A refunded payout can never be sent.
</Callout>

Track completion with the [`PAYOUT_SUCCESSFUL` webhook](/webhooks/payout-successful)
rather than polling. If you need to check state on demand — reconciling after an
outage, say — use [Retrieve a payout](/payouts/get-single-payout) or
[Get payout status](/payouts/get-payout-status).

## Errors

| Status | Cause |
| ------ | ----- |
| `400` | A field failed validation: `amount` below `0.01`, an unsupported `network`, an invalid `toAddress`, or a `merchantReference` you have already used |
| `400` | `Insufficient balance` in the API account for that token |
| `400` | `Insufficient network liquidity`: the API account has enough of the token, but the network you pay out on does not. See [Network liquidity](/API-account/get-network-liquidity) |
| `400` | The payout could not be accepted, for example a recipient that is a Knit account |
| `401` | Missing or invalid token, IP not allow-listed, or missing `payouts:write` |
| `404` | `Wallet not found for the specified token` — no API account exists for that token yet |

All of these are `400`, but the bodies differ. A validation failure carries an
`errors` object naming the offending fields. A reused `merchantReference` is
always named in `message`, even when another field also fails:

```json filename="400 — validation failed"
{
  "message": "The merchant reference has already been taken.",
  "errors": {
    "merchantReference": ["The merchant reference has already been taken."]
  }
}
```

A rejected-but-valid request carries the standard envelope and no `errors`:

```json filename="400 — insufficient balance"
{
  "statusCode": 400,
  "message": "Insufficient balance",
  "data": null,
  "success": false
}
```

Branch on the presence of `errors` to tell them apart — see
[Requests & responses](/conventions#validation-errors).
